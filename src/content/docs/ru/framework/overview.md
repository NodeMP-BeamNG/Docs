NodeMP построен по модульному принципу: компактное, быстрое ядро и открытая система плагинов.

Ядро сервера (`Node-Server`) — это отдельный процесс, слушающий один порт по TCP и UDP (по умолчанию `30814`, задаётся в `server.toml`). Оно берет на себя всю рутину мультиплеера: принимает подключения, ретранслирует состояние машин (позиции, повреждения, авторитет управления и блокировки), раздает моды и доставляет клиентские скрипты.

Вся прикладная логика — будь то экономика, мини-игры или администрирование — вынесена в плагины: скриптовые ресурсы на Lua или JavaScript и нативные модули на C или C++.

## Роль директории

Директория (`api.nodemp.com`) — центральный веб-сервис, у которого две простые задачи: публиковать сервер в общем списке лаунчера по периодическим маякам и проверять аккаунты игроков. Если на сервере разрешён Test Drive (`TestDrive = true`), зайти можно и без аккаунта.

При этом сервер полностью работоспособен и автономно, без связи с директорией. В таком режиме он не отображается в общем каталоге, а игроки подключаются напрямую по IP-адресу через вкладку **Direct Connect** в лаунчере.

## Транспорт

Компоненты общаются на двух уровнях — локальном и сетевом:

```
client mod   <-- local TCP 4444 (commands) + 4445 (traffic)  -->  helper
helper       <-- TLS 1.3 (TCP) + low-latency UDP (positions) -->  Node-Server
Node-Server  <-- HTTPS                                       -->  directory
```

Команды и надёжное состояние идут по зашифрованному соединению TLS 1.3 поверх TCP. Движение и позиции машин (`State::Pos`, `State::HeadPose`) идут по UDP с проверкой HMAC у каждого пакета — так задержка минимальна. Сетевой протокол строго типизирован, а совместимость версий проверяется при рукопожатии.

Подробнее о механике движения читайте в разделе [Как работает синхронизация](/ru/framework/sync/).

## Три среды выполнения

Разработчикам доступно три уровня интеграции:

1. **Серверный Lua (или JavaScript).** Основное место для игровой логики. Каждый ресурс получает собственное изолированное окружение с API `node` (`node.on`, `node.players`, `node.vehicles`, таймеры, хранилище). Все обработчики выполняются в едином потоке сервера, поэтому гонки данных исключены. Для поддержки JS используется модуль `js-host`. См. [Справочник API](/ru/plugins/api/).
2. **Клиентский Lua.** Скрипты из папки `client/` автоматически передаются игрокам при входе на сервер и выполняются прямо внутри BeamNG. Они могут добавлять интерфейсы, эффекты или управлять поведением машины на стороне клиента. При выходе с сервера скрипты автоматически выгружаются.
3. **SDK для локальных модов (`NodeMP.*`).** Обычные моды BeamNG, установленные у игрока, могут общаться с сетевым модом через глобальный объект `NodeMP` (получать список игроков, статус сессии и др.). См. [Клиентские скрипты](/ru/plugins/client-scripting/).

## Структура папки ресурса

Каждый плагин хранится в отдельной папке внутри каталога `resources/`:

```
resources/
└── my-gamemode/
    ├── resource.toml
    ├── server/
    │   └── main.lua        # серверная логика (API node)
    └── client/
        └── main.lua        # скрипт, передаваемый игрокам
```

Манифест `resource.toml` описывает ресурс:

```toml
name = "my-gamemode"
version = "1.0"
type = "lua"                 # или "js" (при наличии js-host)

[server]
main = "server/main.lua"

[client]
files = ["main.lua"]         # скрипты для отправки клиентам
```

## Нативные модули

Если требуется максимальная производительность или низкоуровневые возможности C/C++, используются нативные модули — динамические библиотеки (`.dll` или `.so`) в папке `modules/`. Они позволяют встраивать альтернативные языковые среды (как в `js-host`), выносить тяжёлые вычисления из потока Lua и многое другое.

Подробнее см. в [Справочнике API](/ru/plugins/api/) (C ABI).

## Контент

Моды и карты для сервера помещаются в папку `content/` в виде обычных zip-архивов. Сервер сам проверяет их хеши и раздает недостающие файлы подключающимся игрокам.

При необходимости контент можно защитить: параметр `[Content] Encrypt = true` включает шифрование архивов по ChaCha20 со случайным ключом сессии, а клиент удаляет временные копии сразу после отключения. См. [Ресурсы и контент](/ru/hosting/resources/).

## Ретрансляция

Сетевые события от игроков не транслируются всем подряд напрямую. Клиент отправляет событие на сервер через `node.emitServer`, а серверные плагины решают, кому и какие данные пересылать.

При этом стандартные игровые механики — зажигание, захват узлов, триггеры и права на управление машинами — ядро синхронизирует самостоятельно. Если же требуется разделить игроков на изолированные миры или сессии, достаточно использовать встроенные группы видимости ядра: сетевой трафик между разными группами никогда не пересекается.
