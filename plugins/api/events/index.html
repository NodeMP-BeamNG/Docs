Plugin development

Events reference

Generated from sdk/api.toml by sdk/tools/apigen.py docs. Do not edit; edit the schema.

All of these are subscribed with node.on(name, fn) (C: the register_*_event family), except where an entry names another function. Handlers receive objects and decoded payloads as listed under Handler arguments; node.raw.on delivers the Raw arguments (ids and strings) instead. Handlers run on the plugin worker thread, one at a time. Read Events for the model; this page is the list.

Names follow two rules: a notification reads <subject><Verb-ed> (playerJoined, vehicleSpawned), a request a handler can deny reads <subject><Action>Request (playerConnectRequest, relayRequest). An event that was renamed lists the spelling it was renamed from under Formerly. That old name does NOT work: subscribing to it is refused with an error naming the new one (event "onPlayerConnectRequest" was renamed to "playerConnectRequest"), from Lua and from C, rather than quietly becoming a wire subscription that never fires.

Engine events (observe)

Section titled “Engine events (observe)”

Fired by the server after something happened. Handlers get the subject – a Player or a Vehicle object – or nothing where there is none (serverTick, serverShutdown); return values are ignored. Subscribe with node.on(name, fn). (node.raw.on hands the raw id instead.) Names read <subject><Verb-ed>.

playerAuthenticated

Section titled “playerAuthenticated”

Handler arguments: player
Raw arguments (node.raw.on): playerId
Formerly: playerConnecting (removed – subscribing to it is refused)

A client has authenticated and passed playerConnectRequest; it is about to receive the join replay. Its name and IP are readable already; it has no vehicles yet.

playerJoining

Section titled “playerJoining”

Handler arguments: player
Raw arguments (node.raw.on): playerId

The player’s content is synced and the map went out: its game is loading the level now (server 1.8.0). Fires once per join, after playerAuthenticated and before playerJoined, never for a player playerConnectRequest refused; player.synced is still false and it has no vehicles. The place to start a join timer or show others that someone is loading in. The order is playerConnectRequest, playerAuthenticated, playerJoining, playerJoined.

playerJoined

Section titled “playerJoined”

Handler arguments: player
Raw arguments (node.raw.on): playerId
Formerly: playerJoin (removed – subscribing to it is refused)

The client finished joining: the world replay was delivered and it is now a normal participant. The usual place to greet, assign a role, or restore per-player state.

playerLeft

Section titled “playerLeft”

Handler arguments: player, reason
Raw arguments (node.raw.on): playerId, -1, reason

The client disconnected (quit, kicked, banned or timed out). Its unicycle is deleted (one vehicleDeleted); its cars STAY in the world ownerless (spawner -1), simulated by the best available client or idle until one joins – a resource that wants them gone deletes them itself. The id will be reused by a later player. Since server 1.6.0 only a connection that ends with a FIN (the player left) or a kick fires this at once: after a reset or silence the slot is held for [network] disconnect_sec for a session resume – the player stays connected, keeps its cars, and is reported by playerLagging after lag_grace_sec – and this fires when the window runs out; a resumed session never fires it (nor playerJoined). A launcher up to 1.1.14 can end an ordinary quit with a reset, so time billed up to this event can include that window – unless the player joins again first: a new login of the same directory-verified account releases a slot held that way (lagging, or its link broken) at once, and this fires with reason “Replaced” BEFORE the new player’s playerAuthenticated (the new one may get the same id). A second login while the first is live joins beside it, as before; guests are never matched. reason (server 1.6.0) is why the session ended, the same text as the leave line of the log: “Replaced”, “Connection closed by the client”, “Timeout (silent 31 s)”, “Connection lost (not resumed within 30 s)”, a kick’s own text, and so on; match “Replaced” exactly and treat the rest as prose. Raw arguments are (playerId, -1, reason): a one-argument C subscription (register_builtin_event) still receives the player id, and register_vehicle_event observes all three.

playerFrozenChanged

Section titled “playerFrozenChanged”

Handler arguments: player
Raw arguments (node.raw.on): playerId

A resource froze or thawed the player (Player:freeze, server 1.8.0); player.frozen says which. Fires only on a change.

serverTick

Section titled “serverTick”

Handler arguments: none
Raw arguments (node.raw.on): -1

Once per server tick on the plugin worker. The single argument is always -1. Keep it cheap: this shares the thread with every other handler.

serverShutdown

Section titled “serverShutdown”

Handler arguments: none
Raw arguments (node.raw.on): -1
Formerly: onShutdown (removed – subscribing to it is refused)

The server is stopping. Flush what you must; timers and coroutines will not run again. Plain pg.exec / pg.query statements issued from the handler are drained to the database before the pool closes, but their callbacks do not run (the worker has stopped; the server logs how many were dropped), and a callback-form pg.tx cannot commit – its coroutine needs the worker between BEGIN and COMMIT, so the pool rolls it back. The argument is -1. Each resource’s own resourceUnload(“shutdown”) follows it.

resourceUnload

Section titled “resourceUnload”

Handler arguments: reason
Raw arguments (node.raw.on): -1, -1, reason

THIS resource is about to be unloaded (server 1.2.0): its Lua state is dropped right after every handler returned. reason is “reload” – node.resources.reload (or a reload from the console) is replacing the resource, and the new instance’s entry point runs after this – or “shutdown” – the server is stopping, and this follows serverShutdown. Dispatched synchronously and to the unloading resource’s handlers only, never to another resource’s. The same limitations as serverShutdown: node.storage writes are kept (in memory at once, so the new instance reads them; flushed to disk before the server exits) and plain pg.exec / pg.query statements are delivered, but callbacks, timers and coroutines started here will not run again – put nothing after an await. Raw arguments are (-1, -1, reason): observe it from C with register_vehicle_event (the three-argument form; a native module is never a resource, so a hosted resource of another language host is the only C-side subscriber that ever hears it).

consoleInput

Section titled “consoleInput”

Handler arguments: line
Raw arguments (node.raw.on): -1, -1, line

A line typed into the server console that no built-in command took (server 1.11.0). Handlers run on the worker thread with the whole line, in subscription order. A handler that returns a string, or an array of strings, has it printed back on the console; true means handled with nothing to print; nil means not this handler’s. When no handler answers, the console says “unknown command”. “help” is offered too, after the built-in list, so a resource can list its own commands. Nothing a player sends ever reaches it: the console is the host’s. node.console.command is the convenient form. Raw arguments are (-1, -1, line); a C subscriber (register_vehicle_event) sees the line but cannot answer.

vehicleSpawned

Section titled “vehicleSpawned”

Handler arguments: vehicle
Raw arguments (node.raw.on): globalId

A vehicle entered the registry – spawned by a player (after vehicleSpawnRequest allowed it) or by node.spawnVehicle. The record is readable via node.getVehicle.

vehicleDamageChanged

Section titled “vehicleDamageChanged”

Handler arguments: vehicle
Raw arguments (node.raw.on): globalId

The vehicle’s damage blob changed (the authority sent a new one). Read counters and the blob with node.getVehicleDamage.

vehicleTagsChanged

Section titled “vehicleTagsChanged”

Handler arguments: vehicle
Raw arguments (node.raw.on): globalId

A plugin set or removed a tag on the vehicle. Read the new set with node.getVehicleTags.

vehicleLockChanged

Section titled “vehicleLockChanged”

Handler arguments: vehicle
Raw arguments (node.raw.on): globalId

The vehicle’s lock changed – a plugin set or released it, or the spawner’s Session::Policy applied to a car no plugin owns. Read the new mode, whitelist and owner with node.getVehicleLock.

playerPolicyChanged

Section titled “playerPolicyChanged”

Handler arguments: player
Raw arguments (node.raw.on): playerId

The player’s vehicle policy (Session::Policy, wire v21: the lock it wants on the cars it spawns, and whether others may use their triggers or grab their nodes) arrived or changed. Read it with player:policy(). Not fired for a packet the server rejected.

vehiclePositionChanged

Section titled “vehiclePositionChanged”

Handler arguments: vehicle
Raw arguments (node.raw.on): globalId

The vehicle’s sync authority sent a position snapshot – 60 Hz per vehicle while it is simulated. Read it with getVehicleTransform (and getVehicleControls when hasControls). Fired per accepted packet, COALESCED: at most one dispatch per (event, id) is pending at a time, so a handler that keeps up sees every packet and one that lags sees fewer, never a growing queue. Nothing is posted when nobody subscribed. The argument is the id only: read the data with the getter, which hands back the LATEST cached state – that is what makes coalescing lossless. For a radar or minimap prefer getVehicleTransforms on a timer: one read for every vehicle instead of one event each.

playerInputsChanged

Section titled “playerInputsChanged”

Handler arguments: player
Raw arguments (node.raw.on): playerId

The player, driving, sent new inputs: a position snapshot carrying its controls (60 Hz) or an extra-axes delta. Read everything with getPlayerInputs. Fired per accepted packet, COALESCED: at most one dispatch per (event, id) is pending at a time, so a handler that keeps up sees every packet and one that lags sees fewer, never a growing queue. The per-player form of vehicleInputsChanged / vehiclePositionChanged for tools that think in players, not cars.

vehicleTeleported

Section titled “vehicleTeleported”

Handler arguments: vehicle
Raw arguments (node.raw.on): globalId

A position snapshot carried the teleport flag: the vehicle jumped – a reset, a recovery, a server teleport – rather than drove. One event per such snapshot (rare), not coalesced. getVehicleTransform shows where it landed.

vehicleBreakGroupsChanged

Section titled “vehicleBreakGroupsChanged”

Handler arguments: vehicle
Raw arguments (node.raw.on): globalId

The vehicle reported break groups (parts detaching, glass breaking). Read the merged set with getVehicleBreakGroups. One event per report; they are sent only when something breaks.

playerCameraChanged

Section titled “playerCameraChanged”

Handler arguments: player
Raw arguments (node.raw.on): playerId

The player’s camera moved to another vehicle – its own or one it spectates. Read the target with getPlayerCamera. One event per report. In a strict session (player:setStrict, ABI 1.12) a report that targets a vehicle the player does not occupy is not relayed to the other clients; it still fires this event, and the record player:camera() hands back then carries denied = true (absent otherwise) – the spectate attempt an audit wants to see. The argument cannot carry the flag itself: the event’s single argument is the player id, as for every engine event.

Notifications (observe, with data)

Section titled “Notifications (observe, with data)”

Fired AFTER the server acted on something a player did – relayed and cached an action on a vehicle, or judged a report the player’s launcher sent. Handlers get (player, vehicle, payload) – the payload decoded into a table where it is JSON, a string where it is a role name (see each event); where no vehicle is involved the raw argument is a fixed -1 and the handler gets (player, payload); return values are ignored. C observes them with register_vehicle_event.

playerLagging

Section titled “playerLagging”

Handler arguments: player, silentSec
Raw arguments (node.raw.on): playerId, -1, silentSec

Nothing has arrived from the player for [network] lag_grace_sec (server 1.6.0): no TCP frame, no datagram from its bound UDP endpoint. silentSec is how long it has been silent, in seconds with one decimal. The player is NOT gone: its id, name, seat, cars and sync authority are all kept – another player may take its driver seat only after seat_takeover_sec, the server releases seat and authority after seat_release_sec, and the player leaves (playerLeft) after disconnect_sec of silence, or once its TCP link broke and it did not resume the session within disconnect_sec. Every other client receives the wire event player:lagging {pid, silentSec} at the same moment, so the mod can freeze and ghost the car. Fired once per silence; playerRecovered ends it. player:isLagging() answers true in between. Observe-only.

playerRecovered

Section titled “playerRecovered”

Handler arguments: player, silentSec
Raw arguments (node.raw.on): playerId, -1, silentSec

The first packet from a player that was lagging (playerLagging) arrived – over the same link, or over a new one after the launcher resumed the session (server 1.6.0). silentSec is how long it was silent in total. The other clients receive player:recovered {pid, silentSec}; the player’s next position snaps its car to where it really is. Observe-only.

serverShutdownScheduled

Section titled “serverShutdownScheduled”

Handler arguments: json (table)
Raw arguments (node.raw.on): -1, -1, json

A resource scheduled a stop with node.server.shutdown(reason, delayMs) (server 1.8.0): data = {reason, at (unix seconds), by (the resource’s name)} – the moment to announce a countdown – or {cancelled = true, by} when a scheduled stop was called off. A stop with no delay does not fire it; serverShutdown follows as for any stop.

vehicleDeleted

Section titled “vehicleDeleted”

Handler arguments: vehicle, cause
Raw arguments (node.raw.on): playerId, globalId, cause

A vehicle left the registry. cause says why (ABI 2.2): “player” (the client deleted its own car), “server” (delete_vehicle / delete_all_vehicles), “leave” (the leaver’s walking avatar; its real cars stay, see playerLeft), “seat” (the avatar of a player who took a seat), “replace” (an avatar edited into a real car). The record is gone by the time this fires; anything you cached about it is now yours alone. A one-argument C subscription (register_builtin_event) still receives the vehicle id.

vehicleRespawned

Section titled “vehicleRespawned”

Handler arguments: player, vehicle, config (table)
Raw arguments (node.raw.on): playerId, globalId, configJson

The player replaced its own vehicle in place (a SpawnReq naming the car it drives): the registry holds the new config and everyone received the Spawn. data is the new config JSON. vehicleSpawned fires for NEW cars only, so this is the completion of a swap (ABI 2.2).

vehicleEdited

Section titled “vehicleEdited”

Handler arguments: player, vehicle, config (table)
Raw arguments (node.raw.on): playerId, globalId, configJson

The player changed the vehicle’s configuration (parts, tuning) and the server relayed and cached it. data is the new config JSON text – the same the joiner replay carries, also when the edit came as a batch of changes.

vehicleReset

Section titled “vehicleReset”

Handler arguments: player, vehicle, posRot (table)
Raw arguments (node.raw.on): playerId, globalId, posRotJson

The vehicle was reset. data is the position/rotation JSON it was reset to plus cause: “player” (the driver pressed reset / recover; player is the driver) or “server” (vehicle:reset from a resource; player is nil / -1). Observe-only: there is no clean previous value to restore, so it cannot be denied.

vehiclePainted

Section titled “vehiclePainted”

Handler arguments: player, vehicle, paints (table)
Raw arguments (node.raw.on): playerId, globalId, paintsJson

The player repainted the vehicle and the server relayed and cached it. data is the paints JSON.

playerSeatChanged

Section titled “playerSeatChanged”

Handler arguments: player, vehicle (nil on foot), role, seat
Raw arguments (node.raw.on): playerId, globalId|-1, role, seat

A player’s seat changed: entered or left a vehicle, moved to another seat of it, was seated/unseated/swapped by the server, or took over a vehicle after its authority left (grace takeover). globalId is -1 when the player is now on foot; role is “driver”, “passenger” or “none”. seat (Lua only, wire v24) is the seat id of the car’s layout the player holds now, “” on foot or in a car that reported no layout; a C observer reads it from get_player_vehicle_json.

chatMessage

Section titled “chatMessage”

Handler arguments: player, msg (table)
Raw arguments (node.raw.on): playerId, -1, msgJson

A player’s chat line was decided (server 1.6.0): msg is { text, scope, sent, mid?, code?, reason?, cid? } – the final text and scope, sent = true with the server message id mid it was relayed under, or sent = false with code “muted” / “filtered” / “blocked” (a chatMessageRequest handler refused it; reason is what it said) or “empty” / “invalid” (a rewrite left nothing, or not UTF-8), or “handled” (a resource took it as its command, server 1.8.0). Fired after the relay, on the worker; observe-only. Lines refused before any resource saw them (the per-player rate limit, a malformed body) do not fire it. The place to log chat, feed a Discord bridge or count activity: the decision is final here, unlike in chatMessageRequest, where a later handler may still refuse.

vehicleCouplerChanged

Section titled “vehicleCouplerChanged”

Handler arguments: player, vehicle, call (table)
Raw arguments (node.raw.on): playerId, globalId, callJson

A coupler/door operation by the player was accepted, merged into the cache and relayed; data is the coupler call JSON. The after-the-fact twin of vehicleCouplerRequest, for resources that log or react rather than decide. Skipped entirely when nobody subscribed.

vehicleControllerChanged

Section titled “vehicleControllerChanged”

Handler arguments: player, vehicle, call (table)
Raw arguments (node.raw.on): playerId, globalId, callJson

One controller call from the vehicle’s driver or authority was accepted and merged (lights, wipers, a mod’s controller); data is the call JSON {controllerName, functionName, …}. Sent by clients only when a call changes, so sparse in practice. Skipped entirely when nobody subscribed.

playerVerifyReported

Section titled “playerVerifyReported”

Handler arguments: player, report (table)
Raw arguments (node.raw.on): playerId, -1, reportJson

The player’s launcher helper reported a game-install check (ABI 1.12): the one every join runs at the level [integrity] verify asks for, and every mid-session one – requested with player:verify(level), or run by the helper on its own schedule or after a file changed. No vehicle is involved (the raw second argument is a fixed -1, which the handler does not see). report is { level = "size"|"scripts"|"full"|"strict", outcome = "clean"|"differs"|"failed", problems = <number of mismatches, as the helper reported it>, detail = <text: the first mismatching paths, or why the check could not run>, manifest = <the hash of the reference manifest the helper checked against; "" unless level is "strict"> }. Fired AFTER the server’s own verdict: a “differs” or “failed” report has already kicked the player when [integrity] verify is not off, so the player may be on its way out when the handler runs – read what you need from it right away (its record, or at least its name, is still there until playerLeft has run). Observe-only; there is nothing to deny.

queueAdmitted

Section titled “queueAdmitted”

Handler arguments: player, json (table)
Raw arguments (node.raw.on): playerId, -1, json

A player from the join queue got its place and is a player now, with an id: after playerAuthenticated, before playerJoining. data = { accountId, name, waitedSec }. Its join takes as long as it takes – nothing times it out while the connection lives; playerJoinSlow says when it takes far longer than joins here usually do, and queueNoShow when it leaves before it entered the world.

queueLeft

Section titled “queueLeft”

Handler arguments: json (table)
Raw arguments (node.raw.on): -1, -1, json

A player left the join queue without a place: data = { accountId, name, reason, position, waitedSec }. reason is the log’s: “Connection closed by the client” when the player cancelled, “Timeout (silent 91 s)”, the text queue_remove gave, “Refused by the install check”, and so on. To wait again it presses Play again and starts at the end.

queueNoShow

Section titled “queueNoShow”

Handler arguments: json (table)
Raw arguments (node.raw.on): -1, -1, json

A player let in from the queue left before it entered the world, and the server did not send it away: data = { accountId, name, count, barredUntil }. count is how many such leaves the account has within [queue] no_show_window_min; at max_no_shows it may not queue for no_show_bar_min, and barredUntil is when that ends (unix seconds; nil otherwise).

playerJoinSlow

Section titled “playerJoinSlow”

Handler arguments: player, json (table)
Raw arguments (node.raw.on): playerId, -1, json

A player has been joining for far longer than joins on this server take: four times the median of the recent ones, and never under 15 minutes. data = { seconds, usualSeconds (that limit), accountId (nil for a guest), fromQueue, gameAttached }. Once per join, said on the console too; the server does nothing about it – a weak machine loading a heavy map for the first time is slow, not wrong.

Cancellable requests (decide)

Section titled “Cancellable requests (decide)”

Fired BEFORE the server performs an action a client asked for. Handlers get (player, vehicle, payload) – the payload decoded where it is JSON; a handler that returns false – optionally with a reason string as a second value – denies the action, and the first denial wins. Every cancellable name can also be observed: a handler that returns nothing sees the request and changes nothing. Names read <subject><Action>Request.

playerConnectRequest

Section titled “playerConnectRequest”

Handler arguments: player, name
Raw arguments (node.raw.on): playerId, -1, name
Return: false[, reason] denies; an explicit true admits a player past max_players
Formerly: onPlayerConnectRequest (removed – subscribing to it is refused)

A client authenticated and asks to join; data is its name. Denying disconnects it with the reason (shown to the player). Bans are checked before this fires. On a full server (server 1.8.0) it fires too, with player.overCapacity true and the account already known (accountRoles, accountId, identifiers): a Lua handler that returns an explicit true admits the player anyway – a reserved slot – while silence leaves the refusal (“Server full!”) to the server, and one false denies whatever another handler said. A C verdict callback cannot admit: its 0 is a plain allow.

vehicleSpawnRequest

The player asks to spawn a vehicle; data is the spawn config JSON (jbm, vcf, pos, rot, …). The second argument is the id the client proposed, not the final global id. Denying tells the client, which removes the car locally.

vehicleEnterRequest

vehicleCouplerRequest

Raw arguments (node.raw.on): playerId, globalId, callJson
Return: false[, reason] denies

The player operates a coupler or door; data is the coupler call JSON (the client Coupler schema). Denying suppresses the relay and the cache update.

vehicleEditRequest

Section titled “vehicleEditRequest”

Handler arguments: player, vehicle, config (table)
Raw arguments (node.raw.on): playerId, globalId, configJson
Return: false[, reason] denies
Formerly: onVehicleEditRequest (removed – subscribing to it is refused)

The player changed the vehicle’s config. The client applied it optimistically, so a deny does not only suppress the relay: the server sends the initiator the PREVIOUS cached config back and its local change rolls back to the server’s truth. A deny WITH a reason (wire v22) is preceded by Vehicle::EditDeny carrying it, which the client shows; a bare false rolls back silently. An edit that came as a batch of changes (server 1.9, mods 1.7.5 and later) is judged the same way: configJson is the whole config the batch would make, and a deny rolls back only that batch – the cached config the initiator gets keeps every batch accepted before.

vehiclePaintRequest

Raw arguments (node.raw.on): playerId, globalId, paintsJson
Return: false[, reason] denies
Formerly: onVehiclePaintRequest (removed – subscribing to it is refused)

The player repainted the vehicle; optimistic on the initiator like edits, so a deny rolls the paint back to the previous cached one. A deny WITH a reason (wire v22) is preceded by Vehicle::EditDeny (what = paint) carrying it, which the client shows.

vehicleTriggerRequest

Section titled “vehicleTriggerRequest”

Handler arguments: player, vehicle, call (table)
Raw arguments (node.raw.on): playerId, globalId, callJson
Return: false[, reason] denies
Formerly: onVehicleTriggerRequest (removed – subscribing to it is refused)

The player asks the vehicle’s sync authority to execute a controller call or an in-world trigger press (someone else’s doors, hood, levers); data is the call JSON ({controllerName, functionName, variables…} or {t, a, val}). Runs BEFORE the spawner’s own “let others use my triggers” setting (Session::Policy): a Lua handler that returns an explicit true overrides that setting for this request (how a resource lets a car’s key holders in), false[, reason] denies, returning nothing leaves the decision to the setting. A C verdict callback’s 0 is a plain allow, not an override. Server-side node.triggerVehicle does not fire this: the server never asks itself.

vehicleNodeGrabRequest

Section titled “vehicleNodeGrabRequest”

Handler arguments: player, vehicle, grab (table)
Raw arguments (node.raw.on): playerId, globalId, grabJson
Return: false[, reason] denies; NO HANDLER ALSO DENIES
Formerly: onVehicleNodeGrabRequest (removed – subscribing to it is refused)

The player wants to grab, move or release a node of the vehicle with the experimental node grabber; data is the grab JSON. FAIL-CLOSED: unlike every other cancellable, with no handler registered the request is denied, so enabling node grabbing needs a resource that says yes (see the nodegrab-allow example). The client mod’s synced grabber does not take this path; it is Vehicle::Grab, relayed by the core, and its only permission check is the spawner’s Session::Policy grab bit – this hook does not override that stream. Also gated by the server’s node-grab flag (node.isNodeGrabEnabled).

chatMessageRequest

Section titled “chatMessageRequest”

Handler arguments: player, msg (table)
Raw arguments (node.raw.on): playerId, -1, msgJson
Return: false[, reason] refuses; a string replaces the text; { text?, scope? } replaces either; { handled = true } takes the line as a command

A player’s chat line, before the core relays it (server 1.6.0: chat is part of the core, no chat resource needed). msg is { text, scope, cid? }: text already stripped of control characters, valid UTF-8 and clamped to [chat] max_length; scope “global” or “local” (the sender’s visibility group – its dimension – or everyone when groups are not in use); cid the client’s own message id when its mod sent one. Handlers run in registration order and each sees the text as the ones before it left it. return false[, reason] refuses the line: nobody receives it and the sender is told why (chat:refused with a code and the reason as its text, or a system line for a mod older than core chat) – this is the real mute (warden: chat_veto_event = "chatMessageRequest"); the first false ends the chain. The reason names the code the player’s mod shows a fixed localized line for: “muted” or “filtered” as its first word ("muted", "muted: spamming", "Filtered: links are not allowed") gives code “muted” / “filtered” with what follows the colon as the text; any other reason, or none, gives “blocked”. Returning a string replaces the text; a table { text = ..., scope = "global"|"local" } replaces either (any other scope refuses the line as “blocked” rather than relay it to everyone); nothing (or true) lets the line through as it is. A rewritten line is cleaned and clamped again and reaches everyone with edited = true. The core knows no commands (server 1.8.0): a / line comes here like any other, and a resource that implements a command answers { handled = true } – the line is not relayed, the sender’s mod drops it quietly (chat:ack), no later handler sees it, and the resource replies on its own (player:tell); a / line nobody handles is an ordinary chat line. With no handler the line is relayed at once, without a worker round-trip. C: register_cancellable_event receives the msg JSON as data and can refuse (nonzero, reason in the buffer) but not rewrite. The sender’s own line is part of the relay: the mod draws it when it comes back.

queueJoinRequest

Section titled “queueJoinRequest”

Handler arguments: json (table)
Raw arguments (node.raw.on): -1, -1, json
Return: false[, reason] refuses (the player reads reason; none: “Server full!”); a number, or { position = n }, is where the player waits

A signed-in player is about to wait in the join queue of the full server: its ticket is redeemed and the bans checked, and it has no player id. data = { accountId, name, roles, ip, installId (nil unless the directory names the launcher’s installation), position, total } – position is where it would wait, the end. Return false[, reason] to refuse, or a number – or a table with position – to put it there instead (1 = first; the others shift back). Every handler runs; the first refusal and the first place win. A C verdict callback (register_cancellable_event) can refuse; it moves a player with queue_move.

queueAdmitRequest

Section titled “queueAdmitRequest”

Handler arguments: json (table)
Raw arguments (node.raw.on): -1, -1, json
Return: an accountId, or { accountId = n }, names who gets the place; false lets nobody in for now; nothing: queue order

A place is free and players with their mods ready wait for it. data = { free = , candidates = { { accountId, name, position, waitedSec }, … } } – the ready ones only, in queue order; one still downloading keeps its place and is never a candidate. Return the accountId of a candidate to give it the place, false to let nobody in for now (asked again when something changes, at most once a second), or nothing for the first candidate. A C verdict callback’s nonzero is false.

The relay filter

Section titled “The relay filter”

One hook that is neither an event nor a request: a question the relay asks per packet. It is named like the requests, relayRequest, because false from a handler decides something – here, that one receiver does not get one packet.

relayRequest

Section titled “relayRequest”

Handler arguments: fromPlayerId, toPlayerId, category, subtype, globalId
Return: false hides the packet
C: register_relay_filter
Formerly: canRelay (removed – subscribing to it is refused)

Consulted per (sender, receiver, packet category, subtype, vehicle) before a relay; return false to hide the packet from that receiver. Verdicts are cached, so call node.invalidateRelayCache when the data your hook reads has changed. Subscribed through node.on(“relayRequest”, fn) – or node.relay.filter(fn) – even though it is not a builtin; the handler keeps the raw ids, as this runs on the hot path. Visibility groups are the coarse, cached-for-you alternative.

Wire events from clients

Section titled “Wire events from clients”

Not a fixed list: a resource defines its own wire events by using a name. The same node.on subscribes to them with (player, data); the name not being a builtin is what makes it a wire event.

<domain>:<verb>

Section titled “<domain>:<verb>”

Handler arguments: playerId, data

A wire event a client sent with node.emitServer(name, data) – data is the string the client passed, by convention JSON. Any name that is not a builtin is a wire event; the naming rule is lowercase <domain>:<verb> (chat:send, vehicle:trigger). The same node.on subscribes; emitClient/emitAll send in the other direction. A resource defines its own events simply by using a name. One is the core’s own since server 1.6.0: chat:send { text, scope?, cid? } is relayed by the core (see chatMessageRequest) and reaches chat:send handlers afterwards, unchanged, for every line that passed the rate limit – refused and handled ones included – so a handler that counts activity keeps working; it must not relay the line itself any more (the core drops such a copy).
